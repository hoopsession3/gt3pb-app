What can be erased

You asked for two things: let you delete a brew started by accident, and find everywhere else that should allow deletion and doesn't. Auditing it turned the question inside out. The console is not short of permission to delete — it is short of the distinction between a mistake and a record.

The inversion

Two failure modes were sitting side by side, and they are opposites:

A batch logged by accident
Could not be removed from where the mistake happened. The only Delete was two taps behind a view toggle in the production log.		 An invoice. The stock ledger. The jug ledger.
Could be deleted outright by any account that wasn't a customer — including a server or a contractor.

The reason is one line of SQL written in 2025. is_staff() is defined as role <> 'member', so it is a negation of "customer", not a list of who should be trusted. A server, a contractor, an operator and an event manager all clear it identically — there is no policy anywhere in the database that tells a server apart from a contractor. Forty-one tables sat behind that one check.

Ten tables carried a hard-delete guard before today (from migrations 0141, 0276, 0277, 0281 and 0292 — customer records, equipment, agreements, offers and expenses). Nineteen money- and record-bearing tables carried none.

Who can delete what, by role

Counted from the live database, not from the source. Each row is cumulative — an admin has everything below it plus its own.

Two things the counts don't show. Guard triggers override all of it — a policy can allow a delete that a before delete trigger then refuses, which is why the is_admin() policy on orders has been a dead letter since 0141. And is_admin() still honours a legacy profiles.is_admin boolean regardless of role, so a member row carrying that flag clears an admin gate.

The three answers

Every row in the app is one of these. The mistake was that the code didn't know which was which, so it treated them all the same.

Delete

It never happened and nothing depends on it. A mistyped batch, a stale budget, a draft you thought better of.

Discard

It happened, or something points at it. Keep the row and mark it void, so whatever references it still resolves.

Never

Money, stock, or a legal record. Block the hard delete and correct it with a reversing entry instead.

Shipped today

Migration 0308, applied and verified in production.

Fixed brew_batches
A brew started by mistake can be taken back — from where you notice it

The removal is now on the planned card, in the adjust sheet a brewing batch opens, and in the batch log. All three call one function, so the answer no longer depends on which screen you were on.

discard_batch() decides, not you. Three tables carry batch_id with on delete set null — drop orders, delivery orders, the stock ledger — so deleting a batch something points at would leave those rows alive and orphaned, which is exactly the traceability 0261 exists to provide. Nothing pointing at it: deleted. Something pointing at it: kept, marked discarded, and the toast says which.

Discarded is deliberately not dumped. Dumped means it was really brewed and really poured out — a loss that belongs in yield. Collapsing the two would make every misfired Start look like wasted coffee.

Fixed invoices jug_ledger loop_txns event_sales inventory_ledger inventory_lots shop_orders business_orders business_accounts
Nine money tables now refuse a hard delete

Chosen deliberately: every one has no incoming cascade. A guard on a cascade target doesn't protect the row, it breaks the parent — event_economics cascades from events, and events are deleted from the console, so guarding it would have made every event undeletable. That case is what the new test asserts, because it's the one that would have shipped broken.

The deliberate override still exists (set_config('gt3.allow_hard_delete','on',false)), because a guard nobody can get past when they genuinely need to is a guard someone eventually drops.

Fixed + 11 more
Deleting on the money surface now requires an admin

A restrictive policy ANDs with what's already there — it cannot widen anything and does not touch reading, inserting or editing. Eleven tables moved out of a server's reach: budgets, business_accounts, business_orders, documents, inventory_lots, invoices, jug_ledger, merch_fulfillments, shop_order_items, shop_orders, vip_verifications.

Policies go where cascades exist and triggers go where they don't: a referential action doesn't consult RLS, but it does fire a trigger.

Fixed gtm_drafts
A dead escape hatch, now live

The playbook query has filtered out status = 'retired' since the day it was written, and nothing in the app has ever set it. The filter was written as if the button existed. A play you sketched and thought better of stayed on the playbook forever, looking live. Retire, not delete — the draft carries a discussion thread worth keeping.

Right as it stands — don't change these

expenses is the template everything else should copy: a soft void with a mandatory reason, a guard trigger refusing hard deletes, and an error message that names the function to use instead. It is the only proper void in the app.

orders, drop orders and delivery orders all have real cancel functions for both staff and the customer, each with the right cutoff — a cup order only while it's new, a pack only before pickup, a delivery only before 6pm two days out. Each raises a refund alert when the order was paid.

strategy_decisions and content_versions are append-only on purpose, and both say so in their own UI. That is a decision, not a gap.

archived_at is a real convention here, used consistently across events, stops, vendors, notes, content, recipes, vessels, kegs and shop products — around forty call sites filtering on it. The soft-delete habit is already in the codebase; it just hadn't reached the money.

Checking it yourself

This audit had to be assembled by hand from pg_policy, pg_trigger and a reading of four gate functions. Nobody should have to do that twice, so it's a query now.

ViewAnswers
v_delete_rights Every table, the gate on deleting from it, whether a trigger blocks hard deletes, and whether it has a soft-delete column to use instead.
v_batch_removable Per batch: safe to delete, discard-only, or already discarded — and the counts of what is holding it, so the reason is visible rather than guessed.

Right now: v_batch_removable reports all five batches as safe to delete, and 27 tables carry a delete guard — up from 18 this morning.
